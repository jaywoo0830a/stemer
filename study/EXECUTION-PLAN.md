# 실행 계획 — 교재 대량 적재 + 경제적 생성 (API RAG 공장)

> 기준 문서: [`NEW-STRATEGY.md`](NEW-STRATEGY.md) (아키텍처·단가) +
> [`GEN-PROTOCOL.md`](GEN-PROTOCOL.md) (생성 출력 규약 100% JSON).
> 목표: **기존 9700X/64GB 서버 자원으로 최대한 많은 교재를 적재하고,
> DeepSeek Flash(오프피크) + 출력 프로토콜로 토픽당 ~$0.001 수준으로 생성한다.**

---

## 0. 하드웨어 예산 (변경 없음, 사용량 재분배)

| 자원 | 인덱싱(Phase A/B) | 생성(Phase C·신규) |
|---|---|---|
| CPU 8코어/16스레드 | Docling 파싱 `--jobs 4~6` (워커당 ~4~6GB) | 가벼움: 검색·리랭크·렌더·검증만 |
| RAM 64GB | 파싱 ~30GB + Postgres ~2GB (여유 ~30GB) | **llama-server 제거 → ~30GB 해제** |
| GPU | 없음 (CPU) | 없음 (API) |

**핵심 구조 변화**: 예전엔 "인덱싱 vs llama-server(30GB) 상호 배타"였지만, 생성이 API로
넘어가면서 **그 제약이 사라진다.** → "책 A를 인덱싱하는 동안 책 B를 생성"하는 **파이프라이닝**이
가능해져 전체 처리량이 오른다. 단, 임베딩·파싱과 생성의 CPU 경합만 피하면 된다.

---

## 1. 실행 단계

### Phase 1 — 생성 엔진 전환 (파일럿, 1~2일)

기존 `generate`의 로컬 llama-server 호출부를 **DeepSeek Flash + GEN-PROTOCOL**로 교체.

**버릴 것**
- llama-server 기동/종료(`up.sh`/`down.sh`, `LLM_MANAGED`) — 생성 경로에서 제거.
- "전체 노트 자유 생성" — 출력 통제 안 된 방식.

**새로 만들 것** (기존 레지스트리 `todo→draft→review→done` 생명주기는 그대로 재사용)
- **과목 스키마·예산 JSON**: `study/config/gen_protocol/v1/{core,math,phys,chem,bio}.json`
  (GEN-PROTOCOL §4 키 사전·필드 예산을 기계가 읽는 형태로).
- **과목 고정 가이드(B)**: 과목별 상수 프롬프트 (키 사전·예산 포함) — 절대 변경 금지 상수.
- **클라이언트/검증/렌더**: Flash 호출(`response_format=json_object`) →
  스키마·예산·빈 슬롯 검증 → 슬롯 patch 재요청(≤2회) → 템플릿 렌더 → KaTeX 린트.
- **usage 로깅**: `prompt_cache_hit/miss_tokens` + 토픽당 비용/토큰 저장 (튜닝·대시보드용).
- **개념 블록 라이브러리**: 생성·검증된 개념 블록 저장/조회 (재사용 → 한계 비용 하락).

**전환 안전망**: 기존 로컬 엔진을 환경변수로 롤백 가능하게 남겨 두고(예: `GEN_ENGINE=api|local`),
파일럿 3개 토픽을 양쪽으로 생성해 품질 A/B 비교 후 API로 고정.

**파일럿 성공 기준**: 토픽 3건이 스키마 검증 통과 + KaTeX 린트 통과 + 예산 내 + 사람 검토 통과.

### Phase 2 — 교재 대량 적재 & 인덱싱 (오프라인, 주력)

**청킹 규칙 1회 확정 후 대량 투입** (뒤에서 바꾸면 재인덱싱 비용 발생):
1. NEW-STRATEGY 기준 **300~500토큰 청크**로 프로필 조정(기존 청커는 문자 단위 — 책별 `chunking.<book>.yaml`).
2. **섹션 매핑/토픽 자동 생성**: 책의 목차·섹션을 그대로 토픽 후보로 등록
   → "많은 책" = "많은 섹션 커버"가 되도록.
3. **그림 코퍼스 정비**: 기존 그림 추출을 유지하되 **그림 ↔ 섹션 매핑**(캡션/페이지 기준)을
   만들어 GEN-PROTOCOL 그림 정책(교재 원본만, 서버 부착)을 지원.

**적재 배치 (용량 추정)**

| 항목 | 추정치 |
|---|---|
| 파싱 (텍스트 PDF) | 1~3초/페이지 → 1,000쪽 ≈ 20~40분 (1워커) / `--jobs 4` ≈ 5~10분 |
| VLM/OCR 무거운 PDF | 수 시간/권 → 배치 맨 마지막에 |
| 책 1권 청크 수 | ~1,000쪽 ≈ **2,000~2,600 청크** (~350토큰/청크) |
| 벡터 저장 | 1024차원 float32 ≈ 4KB/청크 → 책당 ~10MB (디스크 부담 없음) |
| RAM | 파싱 워커 4~6GB × `--jobs 4~6` → ~30GB (llama 제거로 여유 확보됨) |

**운영 방식**: inbox에 PDF를 넣고 인덱싱만 돌리는 배치를 **상시/야간** 가동. 책 단위로
registry에 등록·완료 처리되어 **재개 안전**(기존 인프라 그대로). 30~50권 수준이면
수 일의 인덱싱 배치로 충분 — 용량 병목은 파싱 속도지 저장이 아님.

### Phase 3 — 경제적 배치 생성 (오프피크)

**스케줄·동시성**: Flash 오프피크 창 정의를 확인하고, 생성 배치를 그 시간에 몰아서.
동시성은 **스모크 테스트**(1/5/20 동시 호출)로 TPM/RPM·오류율을 측정한 뒤 결정
(문서의 "동시 2,500"은 검증 필요). 로컬은 검색·리랭크·렌더만 하므로 동시성 수십은 무리 없음.

**파이프라인 (토픽 1건)**:
```
토픽 pop(과목/kind/섹션) → 개념 라이브러리 히트? →
  벡터 검색(C) + 섹션 매핑 + 리랭크 →
  프롬프트 조립 [A][B(과목 가이드)][재사용 통지][C][D] →
  Flash(json_object) → 검증(스키마·예산·빈 슬롯) →
  (실패 시 해당 슬롯 patch ≤2회) → 템플릿 렌더 → 교재 그림 부착(섹션 매칭) →
  KaTeX 린트 → notes/ 저장 → draft → usage 로그
```

**비용 전망 (오프피크·프로토콜 예산 typical)**

| 항목 | 비용 |
|---|---|
| 토픽(가이드) 1건 | ≈ **$0.001~0.0015** |
| 책 1권 전 섹션 (~100~200 토픽) | ≈ **$0.2~0.3** |
| 50권 전 섹션 (~7,500 토픽) | ≈ **$10~15** |
| 인덱싱 | $0 (로컬) |

- 피크면 ×2 → 생성 배치는 **오프피크 고정**.
- 개념 블록 재사용률이 오르면 한계 비용은 추가 하락.

### Phase 4 — 품질·예산 튜닝 & 지속 운영

1. **과목별 골든 세트 10건**을 draft→review→done으로 사람 검토.
2. 검토 결과로 **필드 예산 조정**(GEN-PROTOCOL §4의 "실제 출력 10건 후 튜닝" 항목).
3. KaTeX 린트 위반·빈 슬롯 실패율을 로그로 집계 → 프롬프트/가이드 개선.
4. **비용 대시보드**: 토픽당 비용·캐시 히트율·토큰 수를 주간으로 리뷰.
5. 청킹 규칙 변경 시에만 `reindex` — 그 외엔 인덱스 불변.

## 2. 첫 주 실전 일정 (예시)

| 일 | 작업 | 산출 |
|---|---|---|
| D1 | Phase 1: 스키마 JSON·클라이언트·검증·렌더 구현 + Flash 스모크 | 1책 파일럿, 토픽 3건 |
| D2 | 파일럿 품질 A/B + KaTeX/예산 튜닝 → `GEN_ENGINE=api` 고정 | 파일럿 통과 |
| D3~4 | Phase 2: 청킹 프로필 확정, 파일럿 3~5권 적재·섹션 토픽 등록 | 5권 인덱싱 완료 |
| D5~7 | Phase 3: 오프피크 배치 생성 50~100 토픽 + 검토 | 5권분 노트, 예산 v1 확정 |

이후: 배치 단위(5~10권)로 "인덱싱 → 생성"을 돌려 30~50권까지 확장.

## 4. 남은 결정 사항

1. **토픽 자동 생성 범위**: 책의 모든 섹션을 토픽화 vs 교사가 선별 — "최대한 많은 책"의
   정의에 따라 (비용은 섹션 수에 정비례).
2. **problems kind 사용 여부**: 풀이 포함은 비용 2배 수준 — 기본은 exam(가이드)로.
3. **그림 설명 재생성 여부**: 그림↔섹션 매핑에 캡션만 쓸지, VLM 설명까지 다시 돌릴지
   (로컬 VLM은 무료지만 CPU 시간이 큼).
4. **개념 블록 라이브러리 저장 범위**: 전 과목 공용 vs 과목별 — 검색 정확도와 재사용률 트레이드오프.
